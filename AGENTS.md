# Agent notes

## fzf source

`fzf/` is a git submodule pinned to upstream `v0.74.3`. Local changes live in
`patches/fzf/*.patch` and are not committed inside the submodule.

After clone:

```
pnpm install
pnpm run fzf:sync
pnpm run fzf:patch
pnpm run fzf:build
```

- `fzf:reset` — restore the pinned upstream tree
- `fzf:refresh` — rewrite `patches/fzf` from the current `fzf/` worktree
- `fzf:build` — cross-compile the patched checkout into
  `bin/<platform>_<arch>/fzf` (darwin/linux/win32 × x64/arm64).
  `fzf:build --current` builds the host only.

`download-bins` fetches fd only. Do not add a `postinstall` hook for these. VSIX
consumers use `bin/` only.

Patch style: inject or remove lines only. Do not reindent or reformat
surrounding code (`gofmt` will do that).

## Third-party notices

`THIRD_PARTY_NOTICES.md` is generated by `pnpm run notices` from the binaries in
`bin/`, the Go modules linked into fzf, and the npm runtime dependencies (via `pnpm ls --prod`). Rerun
it after rebuilding `bin/` or changing `dependencies`, and commit the result.

## Releases

Run the `Release` workflow manually on `main` and pick a `patch`/`minor`/`major`
bump. It bumps `package.json`, builds the VSIX on
`ubuntu-latest`, then pushes a `Release vX.Y.Z` commit and `vX.Y.Z` tag to
`main` and publishes the VSIX to GitHub Releases (not the Marketplace). Do not
bump the version or create release tags by hand.

Release immutability is enabled for the repository: a published release's tag
and assets can never be changed, and the tag name can't be reused. The workflow
uploads to a draft, publishes it, then fails unless the release is immutable
and `gh release verify` / `gh release verify-asset` pass. Verify a downloaded
VSIX with `gh release verify-asset vX.Y.Z fast-quick-open-X.Y.Z.vsix`.

## Workflow lockfile

Actions used in `.github/workflows/` are pinned in
`.github/workflows/actions.lock`, generated by the `gh actions-lock` extension
(`gh extension install github/gh-actions-lock`). Never edit it by hand. After
adding a workflow or changing any `uses:`, rerun `gh actions-lock` and commit
the lockfile together with the workflow change.

## Tests

`pnpm test` (and `vscode-test`) launches a real VS Code instance. It **fails in a
sandbox** (VS Code cannot start). Run the test suite **unsandboxed**
(`required_permissions: ["all"]`, or equivalent) in the agent session that
executes tests.

Do not assume a sandboxed `pnpm test` result is meaningful.
